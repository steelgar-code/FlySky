## 6. Batch 1b — expected changes

Only `index.html`, the tests and the documentation change. `map.js`, `hazard.js`, `icing.js` and `sw.js` are not touched, so no `?v=` or cache version moves.

### A. A failed model is not asked again on every trigger (F1)

1. A model's failure is remembered in memory, per mode / location / model: when, the error, and whether it was a limit reply. Nothing is saved to storage; a reload starts clean.
2. Automatic triggers ask for a failed model again only after 30 minutes (`MODEL_RETRY_MS`). **Refresh** always asks for every selected model. Models with a fresh record are not asked, as now.
3. A limit reply (HTTP 429, hour or day) is remembered the same way: no automatic retry for 30 minutes. A network failure (offline) is **not** remembered — it is tried again on the next trigger, as before.
4. Messages:
   - "{model} unavailable: {error}" shows when the failure is new and after Refresh; an automatic retry with the same result is silent. The chip's warning mark and "N model(s) missing" in the source line stay.
   - "Offline — showing the last saved forecast" shows only for a network failure.
   - The source line reads "Cached forecast from …" only when the request failed for the network or a limit and saved data is shown instead. A model without data alone leaves "Updated … · 1 model(s) missing".
5. A success for a model clears its remembered failure.

Tests (`tests/forecast-data.mjs`, with a mock option that fails one model): after the first load, further `loadForecast()` calls ask nothing; one toast in all; the source line is not "Cached"; Refresh asks again and says so again; with the remembered time moved back 31 minutes one automatic retry is made, silently.

### B. The confidence names the group it counts (decision 1)

1. Wherever the percentage is shown — the verdict line of the "Can I fly now?" card, the flight bar's hover and pinned line, the confidence strip's cell titles — the text is **"{pct} of members: {verdict}"** in Ensemble mode and **"{pct} of models: {verdict}"** in Models mode. The verdict is the largest group's (`agree.top`), in lower case; the colour still follows the level (high / medium / low).
2. English, Ukrainian and Portuguese (BR) strings. `confHour` goes if nothing uses it.
3. Unchanged: each hour's verdict, the strip's three levels and its legend, the pinned hour's split line and per-model shares, the planner's and "next suitable" tags ("high confidence" — no number).

Tests (`tests/forecast-now.mjs`): 10 % of members wet and the rest fine → the card says "Uncertain" and "90% of members: suitable"; the Models-mode wording; Ukrainian.

README ×3: the *Forecast confidence* bullet says what the percentage is.

### Done when

The targeted suites and then the whole offline suite pass (494 checks plus the new ones), the three READMEs agree, and this page lists batch 1b under *Done* with its commit.

## 7. Batch 1c — expected changes (wind aloft, decision 4)

Today the wind-aloft chart, tile and flight factor use fixed pressure levels: Ensemble mode pools 1000 hPa and 925 hPa and the verdict takes the median of the mix; Models mode uses 950 hPa. Neither follows the flight altitude setting (handoff open item O1).

### A. Models mode: the wind at the flight altitude

1. The wind-aloft values are the wind speed at the **flight altitude above the ground at the forecast location** (`state.flightProfile.heightM`), per model.
   - 10 m and 120 m: the models' height levels (`wind_speed_10m`, `wind_speed_120m`).
   - 200 m and up: the three pressure levels around that height — wind speed and geopotential height, **6 variables, no direction** — with the speed interpolated in height between the level below and the level above; one level alone stands for a height within 250 m of it; a level less than 20 m above the ground is left out. The same rules as the map's `windAt()`, for the speed only.
   - The ground is the elevation in the forecast answer (saved with each model's record). The levels are chosen around it; before any answer is known, around the location's own elevation or 150 m.
2. Cost: 5 more variables than the single 950 hPa one, × 5 default models ÷ 10 ≈ **2.5 calls more** per Models update (≈ 5.5 instead of 3). The cost line in the side menu follows by itself.
3. The level choice and its constants (`STD_LEVEL_HEIGHT`, the 250 m reach, the 20 m rule, `windLevelsFor()`) exist once, in `index.html`, and `map.js` uses them from there. `map.js` keeps its own `windAt()` (it needs the direction).
4. Changing the flight altitude (side menu, map side menu, calculator): the forecast is worked out again at once; a request goes out only when the new height needs levels that the saved records lack (400 m → 500 m needs none).
5. A saved record counts as due when it lacks a variable the mode now asks for — so the records saved before this batch (950 hPa only) are read again once.
6. A model without the nearer levels (ECMWF IFS has neither 975 nor 950 hPa) contributes through the one level it has when that is within 250 m; otherwise it has no wind aloft and the confidence treats it as today.

### B. Ensemble mode: 925 hPa only

1. `wind_speed_1000hPa` is no longer asked or used: one variable less for every member, ≈ 20 calls less per update with the four default ensembles.
2. The chart, tile and factor use each member's 925 hPa wind. The title names the level and its approximate height above the ground at the location (standard height 760 m minus the ground, rounded to 50 m; "~600 m" over a 150 m ground). Where that height is under 20 m the factor is left out, as for a level inside the terrain.
3. The member-level legend (two colours for two levels) goes; members are one colour again.

### C. Labels and documents

1. Titles in three languages: Models "Wind at {h} m" with the levels used as the note; Ensemble "Wind ~{h} m (925 hPa)". The tile ("Aloft"), the thresholds row and the flight factor keep their names.
2. The three READMEs (parameters, flight conditions, requests: the new costs), the handoff document (O1 closed, §5.1 labels), this page.

### D. F2 — the map readout's rain and gusts

The crosshair readout takes precipitation and gusts from the timestamp that closes the hour containing the image (the hour from 14:00 is stamped 15:00), like the forecast view since batch 1a.

### Versions

`map.js` changes: `map.js?v=` up by one in `index.html` and `sw.js`, and the cache name in `sw.js`.

### Tests

- `forecast-now.mjs` / `forecast-data.mjs`: the Models request names the three levels' wind speed and height for 400 m and no direction; the value is interpolated (a mock with known speeds and heights at the levels); 10 m and 120 m use the height levels; an altitude change with the same levels asks nothing and changes the value, one with other levels asks once; a record without the levels is read again; the Ensemble request has no 1000 hPa and the title names 925 hPa with its height; a model with only one level within reach still counts.

- The map's wind and route suites pass unchanged (they prove the shared constants moved without a change in behaviour).

## 9. Why batch 2a

Four things, all about the app staying usable in the field and changes not breaking it:

- **The app opens from its saved copy first.** Today the service worker asks the network for every file and uses the saved copy only after the network has failed. On a connection that is up but very slow, that means waiting tens of seconds for the app to appear. Serving the saved files at once and refreshing them in the background makes the start immediate.
- **A notice when a new version is ready.** Today a new version replaces the old one silently under an open page. That page can then load a newer `map.js` than the `index.html` it was built for — a mix nobody tested. A "new version — reload" notice keeps the two together.
- **A test for the version numbers.** A release means raising `?v=` by hand in `index.html`, in `sw.js`, and the cache name. A forgotten one leaves users on an old file. A test that compares them catches it.
- **Tests on every push (CI), with a lockfile.** The 510 checks run only when someone remembers to run them. A GitHub Actions workflow runs them on every push and pull request and marks the commit red when one fails. The lockfile (`tests/package-lock.json`) pins the exact versions of the test tools, so a run next month uses the same ones as today. Cost: one small workflow file, the lockfile, and about 15 minutes of GitHub Actions time per push (free for public repositories).

The decision asked for is only the last point: add the workflow and commit the lockfile, or leave the tests manual.
